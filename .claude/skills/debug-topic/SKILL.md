## 目标

面对一次可控故障，完成：观察现象 → 定位原因 → 修复 → 重新运行 → 验证恢复。

## 常见故障与排查

### 1. Topic 写错

现象：
- Web 监测台收不到某个断面的消息
- 其他断面正常，只有 reach-x 不更新

排查：
- 对比发布端和订阅端的 Topic 字符串
- 确认 `reach-a/b/c` 拼写一致
- 确认订阅端用 `tidewatch/+/state` 通配符

修复：
- 改回正确 Topic
- 重新发布，确认三端更新

### 2. Broker 停止

现象：
- 所有断面都不更新
- 浏览器控制台报连接失败
- 模拟节点报连接被拒绝

排查：
- 检查 Broker 进程是否还在
- 检查端口 1883 和 8083 是否被占用或未监听

修复：
- 重新启动 Broker
- 确认三端自动重连或手动刷新后恢复

### 3. 发送错误 JSON

现象：
- 前端报 JSON 解析错误
- 状态不更新
- 控制台有 parse error

排查：
- 打印原始消息体
- 检查是否有缺字段、多逗号、引号不配对

修复：
- 修正 JSON，重新发布
- 确认数据质量前置检查能拦住错误消息

### 4. 字段名不一致

现象：
- 消息能收到，但状态不更新
- 前端读不到某个字段，显示 undefined

排查：
- 对比发布端字段名和契约：reachId, waterLevel, turbidity, flowLevel, status, time
- 常见错误：reach_id, water_level, flow_level

修复：
- 统一字段名
- 重新发布，确认更新

### 5. 断面节点长时间不发数据

现象：
- 某个断面一直显示旧状态
- last_seen 很久没更新

排查：
- 检查该节点进程是否还在
- 检查该节点是否卡住或报错

修复：
- 重启该节点
- 确认新消息到达后三端更新

### 6. 移动端不同步

现象：
- Web 更新了，移动端没更新
- 或移动端更新了，Web 没更新

排查：
- 移动端是否订阅了同一套 Topic
- 移动端 Broker 地址是否正确（WebSocket 8083，不是 1883）
- 微信开发者工具是否关闭了域名/TLS 校验
- 真机中 localhost 是否指向手机自身

修复：
- 改用局域网可达地址
- 或确认开发环境配置正确后重新订阅

## 验证标准

- 能根据现象、日志和数据流独立定位至少一个真实故障原因
- 修复后重新跑同一链路
- 三端恢复同步更新
- 故障与修复过程有证据

## 证据

截图、日志、JSON、短视频放入 `Evidence/D4/` 和 `Evidence/Debug/`。
